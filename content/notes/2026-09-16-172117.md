## The Problem

I recently installed Ubuntu on the Mac Mini due to the terrible performance of Docker Desktop. But because of this, I lost the main reason which I had a Mac - which was for iMessage Sift integration.

So how do we use iMessage, without a Mac?

## First Attempt: Pushcut

My first idea was Pushcut which is a small iOS app that turns a webhook into a iOS Shortcut run. Trigger a notification remotely, have it silently run `Send Message` on the phone, no Mac needed.

It worked in principle, but required the phone to be put in 'server' mode. This meant being plugged in 24/7 and with the app open waiting for instructions.

Which might be fine for you. But I built Sift as a companion, meaning I can still use my iPhone as well as the dumbphone.

## What Actually Worked

Good old email. 

```
Processor → SMTP → Email → iPhone (push) → Shortcut → Send Message → Dumbphone
```

A tiny Python server - no dependencies, just `smtplib` from the standard library - takes the same POST request the old Mac gateway used to get, and emails it to my own inbox instead of scripting Messages.app. On the phone, a Shortcuts Personal Automation watches for that email (sender, subject, done - filtered tight enough it won't fire on anything else) and runs `Send Message` to the dumbphone the moment it lands. iCloud's push is what makes it instant instead of waiting on a poll interval.

## The Reverse Channel Got Rebuilt Too

The SMS Assistant - text a command to your iPhone number, get a reply - had the same problem from the other direction. 

Rewrote it to be event-driven instead of polled. A second Shortcuts automation (trigger: message received from the dumbphone, run immediately) POSTs the text straight to a small FastAPI service the moment it arrives. No polling loop, no chat.db, no macOS API of any kind. It runs in a container, so it runs anywhere a container runs.

Most of the commands carried over unchanged - `PING`, `RESET`, `WEATHER`, `TODO`, `BRIEFING`, `CALL`, `NAV`, `TIMER`, `REMIND`, `RINGGO` were all already plain API calls under the hood, nothing Mac-specific about them. `RESET` now SSHes to the Pi directly instead of shelling out locally, which if anything is more reliable than before.

A few commands didn't make the cut. `MESSAGES` read unread counts out of chat.db, which no longer exists in this setup. `LOCATE` depended on a Bark instance I'm not running anymore. `SEARCH`, and the catch-all LLM chat fallback for anything that didn't match a command, both needed Ollama, which isn't part of this deployment - also gone. Text something that isn't a real command now and you just get pointed at `HELP` instead of a chat reply. I don't miss any of the three enough to stand up the dependencies again, but they're easy enough to bring back if you want them and have the infrastructure.

## Rebuilding the Rest of the Pipeline

With the two gateways sorted, the rest of it was mostly just standing the pieces back up on the new cluster instead of a single Mac. The Pi bridging Bluetooth notifications off the iPhone didn't need touching - it already had no opinion about what was listening on the other end of its HTTP POST. The processor moved over as a container, same filtering rules, same dashboard, same everything - it was always just a Python service that happened to live on a Mac, not something that needed one.
